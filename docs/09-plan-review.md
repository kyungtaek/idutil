# 전체 플랜 검토 — 책임·복구·GC 단순화

2026-11-02. 현재 문서와 기존 PoC를 대조한 **설계 검토**다. 제품 구현·설치·새 빌드 시험·정리는 하지 않았다. 아래 정리는 [개발 플랜](05-development-plan.md), 스펙, 매뉴얼, 에이전트 설치, 체크리스트에 반영했다. 조사/PoC는 역사적 근거로 보존한다.

## 1. 유지하는 핵심

Worktrunk가 워크트리를 관리하고 idutil은 관리되는 빌드 공간과 공식 캐시 연결·GC를 담당한다. 빌드는 Xcode/xcodebuild/XcodeBuildMCP가 한다. Tuist는 요구하지 않는다. 각 의존성 방식의 단독/복합 구성을 지원한다. 캐시 문제가 있으면 클린 빌드를 감수하되 새 공간도 동일한 관리 규칙을 따른다.

## 2. 모순 또는 불명확한 부분과 정리

| 발견 | 문제 | 반영한 기준 |
| --- | --- | --- |
| 안정적인 경로 재사용 vs 누락/충돌마다 신규 생성 | 정상 작업 전환·MCP 재시작에도 캐시를 잃을 수 있음 | 도구 설정만 빠지면 유효 binding 재적용. binding/실제 자원 오류만 새 세대 생성 |
| 공개 명령에는 prepare가 없는데 에이전트 복구는 prepare를 요구 | hook 밖 복구의 정식 진입점이 불명확 | prepare 공개. 일반 호출은 재사용, --fresh는 새 관리 세대. status/doctor는 읽기 전용 |
| hook 준비 완료 vs 실제 도구 설정 완료 | hook이 기존 MCP 세션을 직접 바꾼다고 오해할 수 있음 | hook은 context 게시, 에이전트가 기존 도구 설정·확인. 준비/캐시 모드/증거 분리 |
| idutil은 빌드를 실행하지 않지만 자동 오류 복구를 약속 | 모든 외부 실패 감지·재시도를 소유하는 것처럼 보임 | 지원 에이전트가 구체적 오류/경로 검사로 복구 요청. idutil은 공간만 준비 |
| 새 DerivedData로 test-without-building 계속 진행 | 새 경로에 실행할 산출물이 없음 | 필요한 선행 빌드는 기존 도구로 수행. idutil build wrapper 추가 없음 |
| 캐시 사용 불명으로 Worktrunk 제거까지 차단 | 외부 캐시를 남겨둘 수 있는데 업무가 막힘 | 외부 캐시는 GC만 보류. 제거 대상 내부의 직접 손실 위험과 구분 |
| 전용 DerivedData 전체 삭제 vs 실패 증거/배포 자료 보존 | 전용 공간 안에 보호 대상이 함께 있을 수 있음 | 보호 항목 제외, 분리 불가능하면 자원 보류. 전용 폴더라고 무조건 삭제하지 않음 |
| 자동 GC vs 외부 writer의 미협조 | idutil lock/idle/mtime만으로 안전 확인 불가 | 검증된 종료 근거 또는 명시적 정리 구간에서만 삭제. 그 외 후보 표시 |
| 디스크 낭비 해결 vs 공통 native 저장소 삭제 제외 | 전체 디스크 상한까지 제공한다고 오해 가능 | 첫 버전은 자체 전용 데이터 회수. 전역/native cache 크기는 별도 관측·후속 정책 |

생성 hook은 신규 생성에 한정되므로 전환/재개 확인은 에이전트 규칙에 남긴다. MCP 세션 기본값도 문맥 전환 때 갱신할 수 있는 상태이므로 기존 binding 재적용과 실제 데이터 손상을 구분해야 한다. [Worktrunk hooks](https://worktrunk.dev/hook/), [MCP session defaults](https://github.com/getsentry/xcodebuildmcp.com/blob/main/app/docs/_content/session-defaults.mdx)

## 3. 불필요한 복잡성 줄이기

- **자체 seed 저장소는 후속으로 이동.** 원본 수집·전체 tree hash·CoW·불변 게시·전이 입력 검증을 첫 버전에 함께 넣지 않는다. 공식 캐시를 사용해도 각 의존성 방식의 정합성 검증은 유지한다.
- **프로필은 명시적인 작업 용도 단위.** 모든 build setting 조합이나 세션마다 새 폴더를 만들지 않는다. 필요한 동시 writer/툴체인 격리만 검증 후 분리한다.
- **설치 엔진 하나.** 스크립트는 setup의 진입점이며 별도 갱신/제거 구현을 중복하지 않는다.
- **상태는 세 축.** 준비 결과, 공유/전용 모드, 도구별 마지막 증거를 구분한다. 이를 지원하기 위해 별도 에이전트 세션 추적 서버를 만들지 않는다.
- **registry/journal 하나.** 자원·참조·복구 세대·증거는 논리 데이터다. 각각 별도 서비스로 확장하지 않는다.
- **GC 엔진 하나.** 수동 계획/적용과 post-remove 정책 정리는 같은 소유권·보존·사용 검사 절차를 사용한다.

단순화해도 워크트리별 경로 격리, 관리되는 새 공간으로 복구, A 제거 후 B 보존, Claude/Codex 및 두 빌드 도구의 실제 경로 검증은 첫 버전 필수다.

## 4. 아직 검증이 필요한 결정

| 항목 | 문서 단계의 기준 | 구현 시 확인할 것 |
| --- | --- | --- |
| XcodeBuildMCP 지원 버전/모드 | 호출별 경로 또는 독립 세션을 사용 | 설정 우선순위·backend 전달·동시성·재시작 |
| Xcode GUI | 기존 빌드 유지, 별도 경로 설정 | workspace/사용자 설정 범위, CLI와 동시 사용. CLI 시험으로 대체 불가 |
| 외부 사용 종료 | unknown은 GC 보류 | 실제로 인정할 종료 근거와 관측 공백. 부족하면 자동 GC 미지원 명시 |
| native cache 오류 | 의심 연결 제외/격리 | 지원 도구 설정으로 우회 가능한 범위. 모든 오류를 새 DerivedData로 고친다고 보장하지 않음 |
| 입력 변경의 정확성 | 내용 진단/변경 시험, compiler 무효화는 기존 도구 책임 | 동일 크기/mtime 바이너리 등 stale 결과. 모든 변경의 자동 감지 기능은 없음 |
| 보존/용량 기본값 | 관리 전용 데이터에만 적용 | 사용자 업무 주기와 실제 회수량. 보호/사용 중 자원을 용량 한도 때문에 강제 삭제하지 않음 |

이 항목들은 문서 검토로 기술적 타당성이 증명된 것이 아니다. 설치 버전과 실제 프로젝트에서 [구현 후 체크리스트](08-post-implementation-checklist.md)를 수행해야 한다.

## 5. 개발 순서

**경로 연결·관리 복구 → 전용 데이터 GC → 공식 공유 계층 최적화** 순서로 구현을 계획한다. 먼저 A/B의 경로가 섞이지 않고 복구 자원이 관리 아래 남는 것을 증명한 뒤 재사용 효과를 측정한다. 단계별 검증은 첫 버전 전체 지원 조건을 생략하기 위한 것이 아니다.

문서 역할도 구분한다. 05는 범위·책임·동작의 기준, 02는 데이터/계약, 03은 정합성 상세와 명시된 후속 설계, 06은 사용자 설명, 07은 설치/에이전트 전달, 08은 실측 체크리스트다. 01/04는 조사·기존 실험 기록이며 최신 기능 약속으로 사용하지 않는다.
