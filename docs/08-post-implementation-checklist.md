# 구현 후 필수 체크리스트 — DerivedData 격리와 캐시 정합성

2026-11-02. 일부 제품 통합 시험을 수행했다. [실행 결과와 증거](10-implementation-status.md)에 통과·실패·미실행을 분리했다. 아래 체크박스는 실제 Claude/Codex 호스트까지 포함한 전체 통과를 의미하므로, 하위 시험만 통과한 항목은 아직 체크하지 않았다. 기존 PoC나 공식 설명은 제품 통합 시험을 대체하지 않는다.

## 1. 실행 단위와 증거

Claude/Codex × xcodebuild/XcodeBuildMCP의 네 조합을 별도 결과로 기록한다. 설치된 Worktrunk·에이전트 호스트·MCP·Xcode/SDK·macOS 버전, 설정/호출 schema, 프로젝트 구성을 고정한다. 미지원 조합은 이유와 함께 미지원으로 남기며 통과 수에 포함하지 않는다. Xcode GUI는 별도 검증 행을 둔다.

각 시험에 날짜, 기대값, 실제값, 통과/실패/차단/미실행, 로그·설정·출력 증거 경로를 기록한다. 비밀값은 기록하지 않는다. 테스트가 만든 자원만 추적하고 사용자의 기존 전역 캐시는 지우지 않는다.

첫 버전은 공식 캐시 연결과 전용 경로 관리가 대상이다. 자체 seed 저장소 시험은 후속 도입 시 별도 추가하며 현재 필수 항목에 섞지 않는다. 개발 순서는 [플랜](05-development-plan.md)의 A 경로/복구 → B 정리 → C 공유 계층이다.

## 2. 생성 hook과 경로 전달

- [ ] Worktrunk로 A/B를 생성하면 prepare 완료 후 후속 작업이 진행된다. 병렬 hook이 준비 전에 빌드를 시작하지 않는다.
- [ ] A/B의 worktree ID/세대와 DerivedData 절대 경로가 다르고, 같은 작업의 재개에는 경로가 유지된다.
- [ ] build context의 project/workspace와 DerivedData가 모두 같은 대상에 연결된다. symlink/상대 경로를 해석해도 다른 작업/공용 위치로 빠지지 않는다.
- [ ] 생성 hook 결과가 실제 에이전트에 전달되고, 설치된 규칙에 따라 현재 context를 읽는다. hook의 export나 파일 존재만으로 성공 처리하지 않는다.
- [ ] 폴더 준비·도구 설정 확인·실제 사용 관측의 상태가 구별된다. 아직 빌드하지 않은 상태를 실제 사용 검증 완료라고 표시하지 않는다.
- [ ] prepare의 prepared/error, 캐시 모드, 도구별 마지막 증거가 분리된다. status/doctor는 변경을 하지 않으며 증거가 없는 현재 MCP 상태를 안다고 표시하지 않는다.

## 3. xcodebuild 실제 사용

- [ ] A/B 각각의 build와 test 호출에 현재 binding의 `-derivedDataPath`가 명시된다. 사용하는 경우 build-for-testing/test-without-building도 같은 대상을 사용한다.
- [ ] 실제 호출 인수, 유효 build settings, build log, 생성된 build DB/intermediates/products/test 결과의 경로를 함께 확인한다. 설정값 출력만으로 통과시키지 않는다.
- [ ] SYMROOT/OBJROOT/CONFIGURATION_BUILD_DIR 등 프로젝트/호출의 출력 override가 전용 공간을 벗어나거나 다른 작업으로 향하면 충돌을 발견한다. 명시적 보호 산출물 경로는 별도 정책으로 설명한다.
- [ ] 런타임/테스트가 A/B 각각의 기대 코드·리소스를 사용한다. 파일 경로만 맞고 다른 앱/테스트 산출물을 실행하는 경우도 실패다.

## 4. XcodeBuildMCP 실제 사용

- [ ] 설치 버전에서 `derivedDataPath`를 설정하고 session defaults 조회 결과가 binding과 같다. project/workspace의 상충하는 이전 기본값을 남기지 않는다.
- [ ] build, build-and-run, test 등 지원 작업마다 경로가 실제 backend 호출과 출력까지 전달된다. 기본값 조회만으로 통과시키지 않는다.
- [ ] 호출별 인수·extraArgs·프로필·설정 파일·시작 환경의 우선순위에 의해 다른 경로로 바뀌지 않는다. backend가 여러 개면 지원하는 각 모드를 검증하고 미검증 모드는 제외한다.
- [ ] A → B → A 전환, 에이전트 재개, MCP 재시작/기본값 초기화 후 현재 경로를 다시 설정한다. 기존 세션이 파일 변경을 자동 반영한다고 가정하지 않는다.
- [ ] A/B 병렬 작업에서 MCP 기본값 덮어쓰기 경쟁이 없다. 독립 세션 또는 검증된 호출별 명시 설정으로 실행하고 각각의 산출물을 확인한다.
- [ ] MCP가 자체 생성하는 기본 DerivedData 위치가 있더라도 우리 관리 경로를 대신 사용하지 않는다. Xcode IDE bridge 등 다른 backend는 위 검증을 통과하기 전 동일 지원으로 간주하지 않는다.

## 5. 관리되는 새 DerivedData로 복구하는 시험

- [ ] binding 없음·중간 실패·오래된 ID·실제 자원 경로 충돌을 각각 주입한다. 실제 워크트리를 확인한 뒤 prepare가 새 관리 DerivedData를 등록하고 에이전트가 도구에 적용해 빌드까지 진행한다.
- [ ] hook 미승인/생략도 별도 시험한다. 유효 binding이 있으면 재사용하고 없으면 명시적인 지원 prepare 흐름으로 준비한다. hook 신뢰 설정을 우회하거나 기본 공용 위치로 진행하지 않는다.
- [ ] 유효한 binding이 남은 전환/재시작/호출 override 오류는 기존 경로 재적용으로 복구한다. resource ID·용량이 유지되고 불필요한 새 세대가 생기지 않는다. 프로젝트의 추적 설정/전역 설정은 임의 변경하지 않는다.
- [ ] 실제 자원 충돌/오염 또는 binding 자체 손상은 prepare --fresh로 새 세대를 생성한다. 같은 저장소의 다른 워크트리 자원을 재지정하거나 삭제하지 않는다.
- [ ] 새 공간으로 바뀐 뒤 test-without-building/앱 실행에 필요한 산출물이 없으면 에이전트가 기존 도구로 먼저 빌드한다. idutil은 빌드·실행·재시도를 대신 수행하지 않는다.
- [ ] 복구 자원이 정상 생성과 같은 관리 루트·경로 규칙·resource ID·프로필·소유권·참조·journal·보존/GC 정책을 가진다. 실제 사용 전에 등록되고 status 용량 집계와 제거 후 release/GC에 포함된다.
- [ ] 같은 오류에 대한 동시/중복 복구, 복구 중 crash, 재시도에도 새 폴더가 무한히 생기지 않는다. 부분 자원은 journal로 대조 가능하며 다음 빌드는 복구된 경로를 재사용한다.
- [ ] 이전 자원과 다른 작업의 캐시는 보존한다. 이전 자원은 사용 종료·보존 조건 확인 후 GC하고 복구 자원도 동일하게 회수한다.
- [ ] 의심되는 공유 캐시는 재연결하지 않으며, 필요하면 지원 설정으로 비활성화/격리한다. 새 DerivedData만 만들고 동일 오류 cache를 계속 쓰는 복구는 실패다.
- [ ] 복구 성공은 경고와 함께 진행한다. 권한/디스크 부족/관리 상태 등록 실패/도구 경로 적용 불가로 새 공간도 쓸 수 없으면 구체적 원인을 보고한다. 같은 오류를 무한 재시도하거나 컴파일·서명·테스트 실패까지 일괄 캐시 오류로 처리하지 않는다.
- [ ] 실측 중 다른 Xcode 작업이 없는 통제 환경에서 기본 DerivedData 및 MCP 기본 위치의 전후 파일 목록/변경을 관찰한다. **시험 대상의 build DB·중간물·products가 그곳에 생성·갱신되지 않아야 한다.**
- [ ] 의도적으로 허용한 패키지 원본/compilation store의 쓰기는 위 누출과 구별한다. ‘공용 폴더 전체가 0바이트 증가’라는 부정확한 기준을 사용하지 않는다.
- [ ] 통제하지 못한 외부 writer 때문에 변경 출처가 불명확하면 통과가 아니라 차단/재시험으로 기록한다. skill 지시를 우회한 임의 셸까지 기술적으로 막았다고 주장하지 않는다.

## 6. 캐시 정합성

[판정 계약](03-mixed-dependency-consistency.md#8-정합성-판정-계약)에 따라 다음을 확인한다.

- [ ] 자원별 reusable/incompatible/unknown 판정에 내용·출처·관련 환경·검사 시각·이유가 기록된다. unknown을 재사용 가능으로 취급하지 않는다.
- [ ] SCM SPM, local SPM, 원격/개발 Pod, prebuilt binary의 단독 구성과 대표 복합 구성을 각각 시험한다. 사용하지 않는 의존성 관리 도구는 요구하지 않는다.
- [ ] lock이 같아도 local/dirty 소스·리소스·podspec·binary/header/modulemap/interface 변경을 관련 판정에서 구별한다. 동일 크기/mtime 교체도 포함한다.
- [ ] revision·전이 의존성·script/plugin 입력·SDK/architecture/platform/configuration 변경이 관련 계층에 반영된다. 불필요하게 모든 다운로드 원본을 무효화하지 않는다.
- [ ] 부분 생성된 private 자원은 prepared로 게시하지 않으며 감지된 잘못된 공통 캐시 연결은 제외한다. 다른 작업의 정상 캐시는 보존한다.
- [ ] cold 기준과 warm 빌드를 비교해 실제 테스트값·리소스·revision·binary slice가 정확하다. cold 기준은 별도 private 경로와 검증된 native cache 비활성화/격리 방법으로 구성하며 전역 cache를 삭제하지 않는다.
- [ ] A/B가 다른 의존성 값을 동시에 빌드해도 결과가 섞이지 않는다. 컴파일 적중은 도구의 근거가 있을 때만 기록한다.
- [ ] 생성 이후 변경도 시험한다. 기존 빌드 시스템이 stale 결과를 내면 성공 exit code와 무관하게 실패로 기록하고, 제한과 검증된 복구 절차를 남긴다.

## 7. 제거 및 GC 회귀

- [ ] A 제거 후 A의 전용 자원만 정책에 따라 정리되고 B의 전용 경로·공통 참조가 유지된다. 두 빌드 도구로 B를 다시 빌드/테스트한다.
- [ ] pre-remove 뒤 제거 실패, post-remove 누락/중복/지연, 같은 경로 재생성에서 살아 있는 자원을 삭제하지 않는다.
- [ ] 빌드 중/사용 불명인 자원은 정리를 보류한다. 시험 중 프로세스를 임의 종료하거나 사용자 자원을 지우지 않는다.
- [ ] 외부 관리 캐시의 사용 불명은 캐시 GC만 보류하며 그 이유만으로 Worktrunk 제거를 차단하지 않는다. 제거될 소스 트리 내부의 직접 참조/보호 자료는 별도로 검사한다.
- [ ] DerivedData 내부의 등록된 archive/dSYM/실패 증거가 보존된다. 보호 항목을 분리할 수 없으면 전체 자원을 보류한다.
- [ ] 실제 자동 GC 통과에 사용한 종료 근거와 관측 한계를 기록한다. 지원되지 않는 사용 감지 조합은 후보 표시/명시적 정리로 제한하고 mtime나 열린 파일 부재만으로 안전을 주장하지 않는다.

## 8. 완료 판정

필수 항목에 실패·미실행이 남으면 그 조합의 검증을 완료로 발표하지 않는다. 미지원/차단은 성공으로 집계하지 않고 지원 범위를 명시한다. **설치 성공, 빌드 성공, 속도 개선만으로 격리·정합성을 통과시킬 수 없다.**
